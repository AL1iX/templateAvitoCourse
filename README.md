# trip-service

HTTP API для MVP такси-сервиса: создание поездки, получение поездки, завершение
поездки. Это лабораторная работа №1 курса «Разработка микросервисов на Go»
(Avito, осень 2026).

## Стек

- Go 1.27
- PostgreSQL
- [chi](https://github.com/go-chi/chi): HTTP-роутер
- [pgx/v5](https://github.com/jackc/pgx): драйвер PostgreSQL
- [squirrel](https://github.com/Masterminds/squirrel): построение SQL-запросов
- [goose](https://github.com/pressly/goose): миграции схемы БД
- [oapi-codegen](https://github.com/oapi-codegen/oapi-codegen): генерация
  серверных типов и интерфейса обработчиков из OpenAPI-контракта

## Требования

- Go 1.27.1 или новее (указано директивой `go` в `go.mod`)
- Docker (нужен для `tripgoctl`)
- [`tripgoctl`](https://github.com/course-go-autumn-2026/course-infra):
  разворачивает локальный PostgreSQL для этой работы

## Запуск

```bash
tripgoctl cluster start
tripgoctl environment start
make migrate
make run
```

`tripgoctl environment start` создаёт `.env` в корне репозитория с реальным
адресом PostgreSQL. Часть переменных окружения (см. ниже) в этот `.env` не
входит: они не обязательны и при отсутствии принимают значение по умолчанию.

Цели `make migrate` и `make run` сами загружают `.env` из корня репозитория
(`set -a; . ./.env`), отдельно экспортировать переменные не нужно. Значения из
`.env` имеют приоритет над переменными, уже заданными в оболочке. Если `.env`
нет, цели используют переменные окружения как есть. Для запуска без `make`
(например, `go run` или бинарника) переменные нужно экспортировать вручную:
`set -a; source .env; set +a`.

Проверка, что сервис запустился:

```bash
curl -i localhost:8080/health
curl -i localhost:8080/ready
```

## Переменные окружения

Обязательные (без них сервис не запускается):

| Переменная | Назначение |
|---|---|
| `HTTP_ADDR` | адрес, на котором слушает HTTP-сервер |
| `LOG_LEVEL` | уровень логирования (`debug`/`info`/`warn`/`error`) |
| `SHUTDOWN_TIMEOUT` | бюджет на graceful shutdown |
| `DATABASE_URL` | строка подключения к PostgreSQL |
| `DATABASE_MAX_CONNS`, `DATABASE_MIN_CONNS` | размер пула соединений |
| `DATABASE_MAX_CONN_LIFETIME` | максимальное время жизни соединения в пуле |
| `DATABASE_CONNECT_TIMEOUT` | таймаут установки соединения с БД |
| `DATABASE_QUERY_TIMEOUT` | таймаут каждой операции с БД: запроса, `BEGIN` и `COMMIT` (применяется в репозиториях и менеджере транзакций; при превышении запрос завершается ошибкой, клиент получает `500 internal_error`); значение должно быть положительным |

Необязательные, не входят в базовый набор, который требует эта работа,
поэтому `tripgoctl` их не создаёт. При отсутствии сервис всё равно
запускается со значением по умолчанию; если переменная задана, но её
значение некорректно, запуск завершится ошибкой:

| Переменная | Значение по умолчанию |
|---|---|
| `HTTP_READ_TIMEOUT` | `5s` |
| `HTTP_READ_HEADER_TIMEOUT` | `5s` |
| `HTTP_WRITE_TIMEOUT` | `10s` |
| `HTTP_IDLE_TIMEOUT` | `60s` |
| `IDEMPOTENCY_KEY_TTL` | `24h` (срок хранения ключей идемпотентности, должен быть положительным) |

Полный список переменных приведён в `.env.example`.

## API

Реализованы пять операций контракта:

| Метод | Путь | Коды ответа |
|---|---|---|
| `POST` | `/api/v1/trips` | `201`, `200`, `400`, `409` |
| `GET` | `/api/v1/trips/{tripId}` | `200`, `400`, `404` |
| `POST` | `/api/v1/trips/{tripId}/finish` | `200`, `400`, `404`, `409` |
| `GET` | `/health` | `200` |
| `GET` | `/ready` | `200`, `503` |

Ошибки оформлены как `application/problem+json` (RFC 9457) с полем `code`:
`invalid_request`, `trip_not_found`, `trip_completed`, `driver_busy`,
`idempotency_conflict`, `internal_error`.

Тело `POST /api/v1/trips` проверяется до обращения к БД. Поля `user_id`,
`driver_id`, `start_point`, `end_point`, `price` (и `latitude`/`longitude`
внутри точек) обязательны: отсутствующее поле или `null` даёт `400
invalid_request`. Явно переданные нулевые значения (`price: 0`, координаты
`0, 0`) допустимы. Неизвестные поля и любые данные после первого JSON-объекта
(например, второй объект) тоже дают `400 invalid_request`; завершающие
пробельные символы допускаются.

### Идемпотентность

`POST /api/v1/trips` принимает необязательный заголовок `Idempotency-Key`
(UUID). Повторный запрос с тем же ключом и тем же телом возвращает уже
созданную поездку с кодом `200`, а не создаёт вторую. Тот же ключ с другим
телом даёт `409 idempotency_conflict`. Ключ вне формата UUID даёт `400
invalid_request`.

Срок хранения ключа задаётся переменной `IDEMPOTENCY_KEY_TTL` (по умолчанию 24
часа от `created_at`). Ключ старше этого срока считается отсутствующим: повтор
с ним создаёт новую поездку и заново занимает ключ (в том числе с другим телом
запроса), а не возвращает старый ответ. Просроченные строки раз в час удаляются
фоновой очисткой, но корректность от неё не зависит: срок проверяется при
каждом чтении.

## Docker

```bash
docker build -t trip-service .
docker run --rm -p 8080:8080 --env-file .env trip-service
```

Сборка двухэтапная: `golang:1.27-alpine` компилирует статический бинарник,
в финальном образе на `gcr.io/distroless/static-debian12:nonroot` лежит только
он, без Go-тулчейна, оболочки и исходников, процесс запускается от
пользователя `nonroot`. Размер финального образа: 9.07 МБ в сжатом виде,
31.1 МБ на диске (по выводу `docker images`).

Если PostgreSQL поднят на хост-машине (как при локальной разработке через
`tripgoctl`), значение `localhost` в `DATABASE_URL` внутри контейнера
указывает на сам контейнер, а не на хост. Подставьте `host.docker.internal`:

```bash
docker run --rm -p 8080:8080 --env-file .env \
  -e DATABASE_URL="${DATABASE_URL//localhost/host.docker.internal}" trip-service
```

## Решения

### Уровень изоляции транзакций

`Read Committed`. Запрет двух активных поездок у одного водителя обеспечивает
partial unique index на уровне БД, и это не зависит от уровня изоляции.
Внутри `Do` при создании поездки нет операций вида «прочитал, на основе
прочитанного принял решение, записал», которым нужна более строгая изоляция:
решение о ключе идемпотентности принимает один условный запрос
`INSERT ... ON CONFLICT ... DO UPDATE ... WHERE`, а остальные операции
(вставка поездки и истории статусов) независимы. Защиту от двойного `finish`
тоже даёт не изоляция, а условие `WHERE status = 'active'` в самом `UPDATE`.
Более того, именно `Read Committed` делает этот запрос корректным при гонке:
проигравший запрос после коммита победителя перепроверяет условие `WHERE` на
новой версии строки и получает 0 затронутых строк. При `Repeatable Read` или
`Serializable` он получил бы ошибку сериализации (`40001`) и повтор транзакций,
не решая ничего, что не решает `Read Committed`.

### Менеджер транзакций

Пакет `internal/txmanager`, интерфейс `Do(ctx, fn)`. Транзакция помещается в
`context.Context` через неэкспортируемый ключ, чтобы её нельзя было случайно
перепутать с чужим значением в контексте. Репозиторий получает исполнителя
запроса (`*pgxpool.Pool` или `pgx.Tx`) через метод `TxManager.Executor(ctx)`:
он проверяет контекст, и если транзакция там уже есть, использует её, иначе
обращается напрямую к пулу соединений. Если `fn` вернула `nil`, выполняется
`COMMIT`; если вернула ошибку или запаниковала, выполняется `ROLLBACK`, при
панике через `defer`/`recover` с повторным `panic` после отката, чтобы
вызывающий код узнал о ней. Вложенный вызов `Do` определяется по наличию
транзакции в переданном `ctx`: если она уже есть, `Do` не открывает новую, а
выполняет `fn` в существующей.

### Запрет двух активных поездок на одного водителя

Обеспечивает partial unique index:

```sql
CREATE UNIQUE INDEX trips_one_active_per_driver_idx
    ON trips (driver_id)
    WHERE status = 'active';
```

Уникальность требуется только среди строк со `status = 'active'`; завершённых
поездок у водителя может быть сколько угодно. Postgres проверяет это условие
атомарно при `INSERT`, поэтому два параллельных запроса на одного водителя
гарантированно дают одну созданную поездку и одну ошибку `23505`, которую
репозиторий превращает в `409 driver_busy`, а не в `500`. Проверено вручную:
20 параллельных `POST` на одного водителя дают ровно один `201` и девятнадцать
`409`; конкурентный `finish` даёт ровно один `200`, остальные `409`.

### Идемпотентность создания поездки

Таблица `idempotency_keys` (`key UUID PRIMARY KEY`, `request_hash`,
`response_body`, `created_at`) с уникальностью по `key`. Если в запросе есть
заголовок `Idempotency-Key`, обработчик сначала ищет живую (не просроченную,
см. ниже) запись с таким ключом. Если она
уже есть, он сравнивает хэш тела текущего запроса с сохранённым: при
совпадении отдаёт сохранённый ответ с кодом `200`, при расхождении отвечает
`409 idempotency_conflict`.

Если записи ещё нет, обработчик резервирует ключ внутри той же транзакции,
что создаёт поездку: сначала вставляет строку с ключом и хэшем тела (с
пустым телом ответа вместо настоящего), затем создаёт поездку, затем
дозаполняет строку уже реальным телом ответа. Если резервирование не
затронуло ни одной строки, значит параллельный запрос с тем же ключом уже
зарезервировал его внутри своей транзакции (конфликт по первичному ключу с
живой записью). Текущая транзакция в этом случае откатывается
целиком, вместе с уже созданной в ней поездкой, а обработчик заново читает
запись по ключу: чужая транзакция к этому моменту уже точно закоммичена, и
можно вернуть её результат тем же способом, что и при найденной записи
выше. Это тот же приём, что и для запрета двух активных поездок у водителя:
гонка решается уникальным индексом на уровне БД, а не блокировками в коде.

Срок жизни ключа проверяется при чтении: `Get` выбирает запись только если
`created_at > now() - TTL`, поэтому просроченный ключ для обработчика выглядит
как отсутствующий. Резервирование ключа выполняется одним запросом `INSERT ...
ON CONFLICT (key) DO UPDATE ... WHERE created_at <= now() - TTL`: для нового
или просроченного ключа строка записывается (счётчик затронутых строк равен 1),
для живого ключа условие `WHERE` ложно, и вставка ничего не меняет (0 строк),
что обработчик трактует как гонку. При нескольких параллельных запросах с одним
просроченным ключом Postgres блокирует конфликтующую строку, поэтому ключ
занимает ровно один запрос, остальные после его коммита видят уже живую запись
и возвращают её результат.

Фоновая очистка (`DELETE ... WHERE created_at <= now() - TTL`, раз в час и при
старте) безопасна при конкурентной работе с резервированием: обе операции
блокируют строку, а только что переиспользованная строка уже не подходит под
условие удаления, поэтому живой ключ не удаляется.

### Таймаут запросов к БД

`DATABASE_QUERY_TIMEOUT` применяется к каждой операции с БД: репозитории `trip`
и `idempotency` оборачивают контекст в `context.WithTimeout` через
`TxManager.WithTimeout`, менеджер транзакций использует тот же таймаут для
`BEGIN`, `COMMIT` и `ROLLBACK`. Дедлайн строится от контекста запроса (или
транзакции), поэтому не переживает ни запрос клиента, ни внешнюю транзакцию;
внутри транзакции каждый запрос ограничен отдельно. `ROLLBACK` выполняется под
собственным таймаутом и не зависит от отмены контекста запроса, чтобы
оборванный клиентом запрос всё равно освободил транзакцию. Проверка `/ready`
использует отдельный `DATABASE_CONNECT_TIMEOUT`.
