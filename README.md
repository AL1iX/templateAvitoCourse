# trip-service

HTTP API для MVP такси-сервиса: создание поездки, получение поездки, завершение
поездки. Это лабораторная работа №1 курса «Разработка микросервисов на Go»
(Avito, осень 2026).

## Стек

- Go 1.27
- PostgreSQL
- [chi](https://github.com/go-chi/chi): HTTP-роутер
- [pgx/v5](https://github.com/jackc/pgx): драйвер PostgreSQL
- [squirrel](https://github.com/Masterminds/squirrel): построение SQL-запросов
- [goose](https://github.com/pressly/goose): миграции схемы БД
- [oapi-codegen](https://github.com/oapi-codegen/oapi-codegen): генерация
  серверных типов и интерфейса обработчиков из OpenAPI-контракта

## Требования

- Go 1.24 или новее (в `go.mod` указан toolchain `1.27.1`)
- Docker (нужен для `tripgoctl`)
- [`tripgoctl`](https://github.com/course-go-autumn-2026/course-infra):
  разворачивает локальный PostgreSQL для этой работы

## Запуск

```bash
tripgoctl cluster start
tripgoctl environment start
make migrate
make run
```

`tripgoctl environment start` создаёт `.env` в корне репозитория с реальным
адресом PostgreSQL. Часть переменных окружения (см. ниже) в этот `.env` не
входит: они не обязательны и при отсутствии принимают значение по умолчанию.

Проверка, что сервис запустился:

```bash
curl -i localhost:8080/health
curl -i localhost:8080/ready
```

## Переменные окружения

Обязательные (без них сервис не запускается):

| Переменная | Назначение |
|---|---|
| `HTTP_ADDR` | адрес, на котором слушает HTTP-сервер |
| `LOG_LEVEL` | уровень логирования (`debug`/`info`/`warn`/`error`) |
| `SHUTDOWN_TIMEOUT` | бюджет на graceful shutdown |
| `DATABASE_URL` | строка подключения к PostgreSQL |
| `DATABASE_MAX_CONNS`, `DATABASE_MIN_CONNS` | размер пула соединений |
| `DATABASE_MAX_CONN_LIFETIME` | максимальное время жизни соединения в пуле |
| `DATABASE_CONNECT_TIMEOUT` | таймаут установки соединения с БД |
| `DATABASE_QUERY_TIMEOUT` | таймаут запроса к БД (зарезервировано для будущих repository-методов) |

Необязательные, не входят в базовый набор, который требует эта работа,
поэтому `tripgoctl` их не создаёт. При отсутствии сервис всё равно
запускается со значением по умолчанию; если переменная задана, но её
значение некорректно, запуск завершится ошибкой:

| Переменная | Значение по умолчанию |
|---|---|
| `HTTP_READ_TIMEOUT` | `5s` |
| `HTTP_READ_HEADER_TIMEOUT` | `5s` |
| `HTTP_WRITE_TIMEOUT` | `10s` |
| `HTTP_IDLE_TIMEOUT` | `60s` |

Полный список переменных приведён в `.env.example`.

## API

Реализованы пять операций контракта:

| Метод | Путь | Коды ответа |
|---|---|---|
| `POST` | `/api/v1/trips` | `201`, `400`, `409` |
| `GET` | `/api/v1/trips/{tripId}` | `200`, `404` |
| `POST` | `/api/v1/trips/{tripId}/finish` | `200`, `404`, `409` |
| `GET` | `/health` | `200` |
| `GET` | `/ready` | `200`, `503` |

Ошибки оформлены как `application/problem+json` (RFC 9457) с полем `code`:
`invalid_request`, `trip_not_found`, `trip_completed`, `driver_busy`,
`internal_error`.

Не реализовано (задания со звёздочкой): идемпотентность по заголовку
`Idempotency-Key`, многоэтапная Docker-сборка.

## Решения

### Уровень изоляции транзакций

`Read Committed`. Запрет двух активных поездок у одного водителя обеспечивает
partial unique index на уровне БД, и это не зависит от уровня изоляции.
Внутри `Do` при создании поездки нет операций вида «прочитал, на основе
прочитанного принял решение, записал», которым нужна более строгая изоляция:
только два независимых `INSERT`. Защиту от двойного `finish` тоже даёт не
изоляция, а условие `WHERE status = 'active'` в самом `UPDATE`. `Serializable`
добавил бы только накладные расходы на повтор транзакций при конфликтах, не
решая ничего, что не решает `Read Committed`.

### Менеджер транзакций

Пакет `internal/txmanager`, интерфейс `Do(ctx, fn)`. Транзакция помещается в
`context.Context` через неэкспортируемый ключ, чтобы её нельзя было случайно
перепутать с чужим значением в контексте. Репозиторий получает исполнителя
запроса (`*pgxpool.Pool` или `pgx.Tx`) через метод `TxManager.Executor(ctx)`:
он проверяет контекст, и если транзакция там уже есть, использует её, иначе
обращается напрямую к пулу соединений. Если `fn` вернула `nil`, выполняется
`COMMIT`; если вернула ошибку или запаниковала, выполняется `ROLLBACK`, при
панике через `defer`/`recover` с повторным `panic` после отката, чтобы
вызывающий код узнал о ней. Вложенный вызов `Do` определяется по наличию
транзакции в переданном `ctx`: если она уже есть, `Do` не открывает новую, а
выполняет `fn` в существующей.

### Запрет двух активных поездок на одного водителя

Обеспечивает partial unique index:

```sql
CREATE UNIQUE INDEX trips_one_active_per_driver_idx
    ON trips (driver_id)
    WHERE status = 'active';
```

Уникальность требуется только среди строк со `status = 'active'`; завершённых
поездок у водителя может быть сколько угодно. Postgres проверяет это условие
атомарно при `INSERT`, поэтому два параллельных запроса на одного водителя
гарантированно дают одну созданную поездку и одну ошибку `23505`, которую
репозиторий превращает в `409 driver_busy`, а не в `500`. Проверено вручную:
20 параллельных `POST` на одного водителя дают ровно один `201` и девятнадцать
`409`; конкурентный `finish` даёт ровно один `200`, остальные `409`.
