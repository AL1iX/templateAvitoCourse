# trip-service

HTTP API для MVP такси-сервиса: создание, получение и завершение поездки,
сохранение координат и маршрут поездки. Это лабораторные работы №1, №2 и №3
курса «Разработка микросервисов на Go» (Avito, осень 2026). В первой написан
сам сервис, во второй он разложен по слоям, покрыт тестами и подключён к
OpenTelemetry. В третьей добавлены координаты и фоновый опрос поездок, по
которым давно нет координат: сканер по тикеру, ограниченная очередь и пул
воркеров просят устройство водителя прислать координату через Push Service.

## Запуск

```bash
tripgoctl cluster start
tripgoctl environment start
make migrate
make run
```

`tripgoctl environment start` создаёт `.env` в корне репозитория с реальными
адресами PostgreSQL, коллектора и Push Service. Сам сервис `.env` не читает, но цели
`make migrate`, `make run` и `make test-integration` загружают его сами
(`set -a; . ./.env`). Значения из `.env` имеют приоритет над переменными,
которые уже заданы в оболочке, а если `.env` нет, цели используют текущее
окружение. Для запуска без make (`go run`, готовый бинарник) переменные нужно
экспортировать вручную: `set -a; source .env; set +a`. Часть переменных (см.
ниже) в этот `.env` не входит: они не обязательны и при отсутствии принимают
значение по умолчанию.

Проверка, что сервис запустился:

```bash
curl -i localhost:8080/health
curl -i localhost:8080/ready
```

Адреса Jaeger, Grafana и Prometheus печатает `tripgoctl connect`.

Обязательные (без них сервис не запускается):

| `LOG_LEVEL` | уровень логирования (`debug`/`info`/`warn`/`error`) |
| `SHUTDOWN_TIMEOUT` | бюджет на graceful shutdown |
| `DATABASE_URL` | строка подключения к PostgreSQL |
| `DATABASE_MAX_CONNS`, `DATABASE_MIN_CONNS` | размер пула соединений |

| `DATABASE_QUERY_TIMEOUT` | таймаут каждой операции с БД: запроса, `BEGIN`, `COMMIT` и `ROLLBACK` (применяется в репозитории и менеджере транзакций; при превышении клиент получает `500 internal_error`); значение должно быть положительным |
| `PUSH_HTTP_URL` | адрес Push Service: `http` или `https`, с хостом, без логина, query и fragment, например `http://localhost:8090`; его создаёт `tripgoctl` |

`tripgoctl`:

| Переменная | Назначение |
|---|---|
| `OTEL_SERVICE_NAME` | имя сервиса (`trip-service`) |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | адрес коллектора |
| `OTEL_EXPORTER_OTLP_PROTOCOL` | протокол экспорта (`http/protobuf`) |

| `OTEL_TRACES_SAMPLER` | сэмплер трейсов (`parentbased_always_on`) |

Необязательные, не входят в базовый набор, который требует эта работа,
поэтому `tripgoctl` их не создаёт. При отсутствии сервис всё равно
запускается со значением по умолчанию; если переменная задана, но её
значение некорректно, запуск завершится ошибкой:

| Переменная | Значение по умолчанию |
|---|---|
| `HTTP_READ_TIMEOUT` | `5s` |
| `HTTP_READ_HEADER_TIMEOUT` | `5s` |
| `HTTP_WRITE_TIMEOUT` | `10s` |
| `HTTP_IDLE_TIMEOUT` | `60s` |
| `IDEMPOTENCY_KEY_TTL` | `24h` (срок хранения ключей идемпотентности, положительное значение) |

Переменные опроса устаревших поездок. `tripgoctl` создаёт их в `.env` третьей
работы, а если переменной нет, берётся значение по умолчанию. Значение должно
быть положительным, иначе запуск завершится ошибкой:

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `POSITION_CHECK_INTERVAL` | `30s` | период тикера сканера, он же пауза между повторными командами по одной поездке |
| `POSITION_STALE_AFTER` | `60s` | сколько поездка может молчать, прежде чем её начнут опрашивать |
| `POSITION_WORKERS` | `4` | число воркеров, которые ходят в Push Service |
| `POSITION_QUEUE_SIZE` | `100` | ёмкость очереди задач |
| `POSITION_BATCH_SIZE` | `100` | сколько поездок сканер читает из БД за один запрос |
| `PUSH_REQUEST_TIMEOUT` | `1s` | таймаут одной задачи и всех таймаутов HTTP-клиента Push Service |

`PUSH_ADMIN_URL` нужна только для самопроверки
(`curl "$PUSH_ADMIN_URL/admin/behaviour"`), сервис её не читает. Админка
заглушки отвечает на том же адресе, что и `PUSH_HTTP_URL`.

Полный список переменных приведён в `.env.example`.

## API

Реализованы семь операций контракта:

| Метод | Путь | Коды ответа |
|---|---|---|
| `POST` | `/api/v1/trips` | `201`, `200`, `400`, `409` |
| `GET` | `/api/v1/trips/{tripId}` | `200`, `400`, `404` |
| `POST` | `/api/v1/trips/{tripId}/finish` | `200`, `400`, `404`, `409` |
| `POST` | `/api/v1/trips/{tripId}/positions` | `201`, `400`, `404`, `409` |
| `GET` | `/api/v1/trips/{tripId}/positions` | `200`, `400`, `404` |
| `GET` | `/health` | `200` |
| `GET` | `/ready` | `200`, `503` |

Ошибки оформлены как `application/problem+json` (RFC 9457) с полем `code`:
`invalid_request`, `trip_not_found`, `trip_completed`, `driver_busy`,
`idempotency_conflict`, `internal_error`.

Тело `POST /api/v1/trips` проверяет HTTP-слой (`internal/http/trip/create`),
до `usecase` и до любого обращения к БД. Поля `user_id`, `driver_id`,
`start_point`, `end_point` и `price`, а также `latitude` и `longitude` внутри
точек обязательны: если поле отсутствует или равно `null`, ответ `400
invalid_request`. Явные нули (цена `0`, координаты `0,0`) остаются допустимыми.
Неизвестные поля и любые данные после первого JSON-объекта (второй объект,
мусор) тоже дают `400`, а пробельные символы в конце тела допускаются.

### Координаты

`POST /api/v1/trips/{tripId}/positions` принимает `coordinates` (`latitude` и
`longitude`) и `recorded_at`. Тело проверяет HTTP-слой
(`internal/http/position/save`), так же как при создании поездки.
Отсутствующее или `null` поле, неизвестное поле, данные после первого
JSON-объекта и дата не в формате RFC 3339 дают `400 invalid_request`, а явные
нули координат допустимы. Домен отклоняет широту вне `[-90, 90]`, долготу вне
`[-180, 180]` и `recorded_at` дальше минуты в будущем (ровно минута допустима).
Завершённая поездка координат не принимает (`409 trip_completed`), неизвестная
даёт `404 trip_not_found`.

`GET /api/v1/trips/{tripId}/positions` отдаёт весь маршрут без пагинации. Точки
идут по возрастанию `recorded_at`, а при равных значениях по `id`. Для поездки
без координат ответ `{"positions":[]}`. Для неизвестной поездки ответ `404`,
потому что `usecase` сначала проверяет, что поездка существует.

В ответах `Trip` есть поле `last_position_at`. Пока координат не было, ключа в
ответе нет, так же как у `finished_at` у активной поездки.

### Идемпотентность

`POST /api/v1/trips` принимает необязательный заголовок `Idempotency-Key`
(UUID). Повторный запрос с тем же ключом и тем же телом возвращает уже
созданную поездку с кодом `200`, а не создаёт вторую. Тот же ключ с другим
телом даёт `409 idempotency_conflict`. Ключ вне формата UUID даёт `400
invalid_request`.

Срок хранения ключа задаёт `IDEMPOTENCY_KEY_TTL` (по умолчанию 24 часа от
`created_at`). Просроченный ключ считается отсутствующим: повторный запрос
создаст новую поездку и снова займёт этот ключ, даже если тело другое.
Просроченные строки удаляет фоновая очистка раз в час. Корректность от неё не
зависит, потому что срок проверяется при каждом чтении.

## Архитектура

Код лежит в `internal/` и разложен по слоям. На каждое действие (`create`,
`get`, `finish` для поездки, `save` и `list` для координат) заведён свой пакет
с одним и тем же именем в `usecase` и в `http`.

```
cmd/trip-service/             main: читает конфиг, вызывает container.New и запускает результат
migrations/                   миграции goose
internal/
  config/                     разбор и проверка переменных окружения
  container/                  создаёт все зависимости и связывает их вручную
  generated/                  код, сгенерированный из OpenAPI (make generate)
  domain/trip/                поездка, статусы, правила, доменные ошибки
  model/                      структуры, которые ходят между слоями
  usecase/trip/{create,get,finish}/
  usecase/position/{save,list}/
  http/trip/{create,get,finish}/   ручки
  http/position/{save,list}/       ручки координат
  http/domainerror/           единственное место, где ошибка превращается в HTTP-ответ
  http/middleware/            Recover, Tracing, Logging, Metrics
  http/health/                /health и /ready
  http/router/                собирает ручки и middleware в один http.Handler
  gateway/push/               HTTP-клиент Push Service
  worker/positions/           сканер, очередь и пул воркеров
  repository/trip/            SQL-реализация: поездки, координаты, выборка для опроса, ключи идемпотентности
  infra/postgres/             пул pgx и трассировка запросов
  infra/postgres/transaction/ менеджер транзакций
  infra/telemetry/            OpenTelemetry и slog
```

### Кто от кого зависит

Зависимости направлены внутрь. Домен не импортирует ничего из проекта.
`usecase` знает про домен и `model`. Ручки и репозиторий тоже зависят от
домена и `model`, но не друг от друга: ручка не импортирует `repository` и
`infra`, а `usecase` не импортирует `net/http` и `pgx`. Связывает всё только
`container`. Эти правила записаны в `depguard` в `.golangci.yml`, поэтому
нарушение ломает `make lint`.

### Где объявлены интерфейсы и почему

Интерфейс объявляет тот, кто им пользуется, в файле `contract.go` своего
пакета, и он не экспортируется. Например, `usecase/trip/create` описывает
`tripRepository` (`Save`, `GetByID`), `idempotencyStore` (`Find`, `Reserve`,
`Complete`), `txManager` (`Do`) и `tripMetrics` (`TripCreated`). Одна и та же
структура `repository/trip.Repository` подходит и под `tripRepository`, и под
`idempotencyStore`. Ручки объявляют свой `useCase`, роутер свои `createHandler`
и `tripHandler`, `health` объявляет `pinger`.

Компонент `worker/positions` объявляет у себя `staleTripFinder` (его реализует
`repository/trip`), `pushGateway` (его реализует `gateway/push`) и
`positionMetrics` (его реализует `infra/telemetry`). Ручка сохранения
координаты объявляет `canceller`, под который подходит сам компонент.

Так сделано по трём причинам. Потребитель сам формулирует, что ему нужно, и
не привязан к конкретной БД. В тестах интерфейс заменяется моком `gomock`,
БД не нужна. Когда у сервиса появится второй транспорт, он подключится к тем
же `usecase`, а менять `usecase` и репозиторий не придётся. Интерфейсы узкие:
самый большой содержит три метода.

Моки генерируются директивой `//go:generate go tool mockgen ...` в
`contract.go`, лежат рядом в `mocks_test.go` и закоммичены.

### Сборка зависимостей

`main` читает конфиг, вызывает `container.New(ctx, cfg)` и запускает то, что
тот вернул. Всё остальное делает `container`: поднимает телеметрию, пул,
репозиторий, `usecase`, ручки и собирает роутер. Глобальных переменных и
`slog.Default()` в коде нет, логгер и провайдеры телеметрии передаются через
конструкторы. Метод `container.Run` кроме HTTP-сервера запускает фоновый опрос
поездок и очистку просроченных ключей идемпотентности (раз в час). Порядок
остановки описан в разделе «Опрос устаревших поездок».

### Ошибки

Домен возвращает `ErrTripNotFound`, `ErrTripCompleted`, `ErrDriverBusy`,
`ErrIdempotencyConflict` и `*ValidationError`. Остальные слои оборачивают их
через `%w`. Функция `domainerror.Problem(err)` определяет статус и код по
`errors.Is` и `errors.As`, ручки просто передают ей ошибку. Неизвестная
ошибка становится `500 internal_error` без деталей, причина уходит в лог.

### Отступления от примерной раскладки

- `migrations/` лежит в корне репозитория, как и в первой работе.
- Ключи идемпотентности хранит `repository/trip` рядом с поездками, отдельного
  пакета нет. `usecase` видит их через узкий интерфейс `idempotencyStore`,
  отдельный пакет ничего бы не добавил.
- Добавлены пакеты `http/router` и `http/health`. Роутер собирает ручки и
  определяет маршрут для middleware, а `health` не относится ни к одной ручке
  поездки.

## Опрос устаревших поездок

Пока поездка активна, устройство водителя шлёт координаты. Если они перестали
приходить, сервис сам просит устройство прислать координату: отправляет в Push
Service команду `REQUEST_POSITION`. Команда ничего не меняет в поездке, не
отменяет и не завершает её.

### Схема

```
                      каждые POSITION_CHECK_INTERVAL
  +-----------------+     запросы батчами      +------------+
  | сканер          | -----------------------> | PostgreSQL |
  | (одна горутина) | <----------------------- +------------+
  +--------+--------+   устаревшие поездки
           | неблокирующая постановка
           v
  +----------------------------------------------------------+
  | очередь: канал на POSITION_QUEUE_SIZE задач              |
  | + карта "поездка в очереди" (версия задачи, мьютекс)     |
  +--------+-------------------------------------------------+
           |
           v
  POSITION_WORKERS воркеров --> Push Service
                                (POST /api/v1/push, kind=REQUEST_POSITION)
```

Параметры описаны в разделе «Переменные окружения».

### Как это работает

Сканер работает в одной горутине с тикером. Тикер спрятан за интерфейсом,
поэтому в тестах его заменяет ручной. На каждом тике сканер читает выборку
батчами по `POSITION_BATCH_SIZE` строк (`FindStale` в `repository/trip`). Выборка
содержит активные поездки, у которых с последней координаты прошло больше
`POSITION_STALE_AFTER`, а если координат не было, время считается от
`started_at`. Время считает сам запрос, сначала идут поездки, которые молчат
дольше всех, при равном времени по `id`. Следующий батч начинается после
последней прочитанной строки: запрос получает пару «время последней активности,
`id`» и берёт строки, которые больше неё. `OFFSET` не используется, потому что он
заставил бы базу заново пройти все уже прочитанные строки, а при изменениях
между запросами сдвигал бы границу. Если батч вернулся неполным, тик
заканчивается. Если очередь заполнилась, сканер дочитывает текущий батч (лишние
задачи считаются как `dropped`), следующий не читает и ждёт следующего тика. Тики обрабатывает одна
горутина, поэтому новый проход не начнётся, пока не закончился прежний. Первый
проход делается на первом тике, а не при старте: после рестарта опрос
возобновляется сам через `POSITION_CHECK_INTERVAL`, ничего прогревать не нужно.

Очередь устроена как буферизованный канал на `POSITION_QUEUE_SIZE` задач.
Рядом лежит карта «поездка в очереди» под мьютексом, в ней для каждой поездки
хранится версия задачи. Сканер сначала пробует занять запись в карте. Если
запись уже есть, поездка стоит в очереди или обрабатывается, и сканер считает
её как `duplicate`. Если записи нет, он без блокировки кладёт задачу в канал.
Одного канала для дедупликации мало, потому что из него нельзя узнать, что в
нём лежит. Операции над картой атомарны: проверка и запись идут под одним
захватом мьютекса, поэтому сканер, воркеры и ручка координат не гоняются друг с
другом.

Когда приходит координата, ручка сохранения после успешного коммита убирает
запись из карты. Воркер, достав задачу из канала, сначала сверяет её версию с
картой. Записи нет, значит поездке уже пришла координата, и в Push Service идти
не нужно. Версия защищает от такого случая: задачу отменили, сканер на
следующем тике поставил ту же поездку заново, и в канале стало две копии. У
старой копии версия другая, поэтому воркер её отбрасывает. Отменённая задача в
метрики не попадает, воркер пишет только запись уровня Debug.

Воркеров ровно `POSITION_WORKERS`. Они стартуют вместе с сервисом и живут до
остановки, горутина на задачу не создаётся. Каждая задача идёт в Push Service с
таймаутом `PUSH_REQUEST_TIMEOUT`. Запись в карте остаётся на время запроса и
снимается после него, поэтому пока запрос в полёте, ту же поездку никто
повторно не поставит. Исключение: если за это время пришла координата, запись
снимается отменой, и следующий тик может поставить поездку снова, если координата
оказалась слишком старой. Отметку об отправленной команде мы не храним. Если
устройство не ответило, поездка снова попадёт в выборку на следующем тике.
Поэтому период тикера и есть пауза между повторными командами по одной
поездке, и ставить его в секунду нельзя.

Шлюз (`internal/gateway/push`) отправляет `POST /api/v1/push` с
`kind=REQUEST_POSITION`, `recipient_id` равным `driver_id` и `data.trip_id`.
Ожидаемый ответ `202`. У шлюза свой HTTP-клиент, не `http.DefaultClient`:
общий таймаут, ожидание заголовков, установка соединения и TLS равны
`PUSH_REQUEST_TIMEOUT`. Тело ответа закрывается всегда. Ошибки различаются:
сеть и таймауты (`ErrTransport`), коды 4xx (`ErrRejected`) и 5xx
(`ErrUnavailable`). Ретраев и ограничителя частоты нет, это тема лабораторной
работы 5. Попытка одна, ошибка попадает в лог уровня Warn и в метрику
`tripgo.position_requests{result="error"}`.

### Что будет, если очередь заполнена

Сканер никогда не блокируется. Если канал полон, задача отбрасывается и сканер
перестаёт читать следующие батчи этого тика: запись
из карты снимается, растут `tripgo.stale_checks{result="dropped"}` и
`tripgo.position_requests{result="dropped"}`, а в лог уровня Warn пишется
`trip_id`. Поездка при этом не теряется: отметки об отправке нет, поэтому
следующий тик найдёт её снова. У этого решения есть недостаток: при постоянной
перегрузке первыми в выборке снова оказываются самые молчаливые поездки, а
менее молчаливые могут долго ждать. Если активных поездок десятки тысяч, а
очередь на 100 задач, почти все задачи на каждом тике будут отбрасываться.

### Остановка

Шаги с первого по четвёртый видны в `container.shutdown`, пятый выполняет `Container.Close`, который `main` вызывает через `defer` после `Run`. Порядок такой:

1. HTTP-сервер перестаёт принимать запросы и дожидается текущих.
2. Сканер останавливается, новые задачи не появляются, канал закрывается.
3. Воркеры дорабатывают то, что уже лежит в очереди.
4. Останавливается очистка ключей идемпотентности.
5. Закрываются клиент Push Service, телеметрия и пул БД.

Бюджет на всё один, `SHUTDOWN_TIMEOUT`, он отсчитывается от сигнала. Если
сервер не успел остановиться, соединения закрываются принудительно и пишется
Warn. Если воркеры не успели доработать очередь, запросы в полёте прерываются,
остаток очереди отбрасывается и тоже пишется Warn. Насовсем такие задачи не
теряются: отметки об отправке нет, поэтому после рестарта поездки без
координат попадут в выборку на первом же тике. В этом случае процесс
завершается с ненулевым кодом. После остановки в процессе не остаётся
горутин, это проверяет `goleak`.

Порядок нельзя менять. HTTP-сервер идёт первым, потому что запрос, который ещё
выполняется, может сохранить координату и отменить задачу. После остановки
сервера отменять уже некому. Сканер останавливается раньше воркеров, иначе он
продолжал бы класть задачи в очередь, которую воркеры дорабатывают, и канал
нельзя было бы закрыть. Клиент Push Service закрывается после воркеров, потому
что они ходят через него.

Сканер и воркеры останавливаются по контексту. Но в `Start` контейнер передаёт
не контекст сигнала, а отдельный, который он сам отменяет на втором шаге, после
остановки HTTP-сервера. Если бы сканер слушал контекст сигнала, он остановился бы
раньше сервера, и порядок из списка нарушился бы. Отмена контекста закрывает
канал, воркеры дорабатывают очередь, `Stop` дожидается их в пределах бюджета.
Запросы к Push Service идут с контекстом без отмены родителя, поэтому отмена
сканера их не обрывает, они прерываются только по истечении бюджета.

### Телеметрия

| Метрика | Тип | Лейблы | Что показывает |
|---|---|---|---|
| `tripgo.positions.saved` | counter | нет | сохранённые координаты |
| `tripgo.stale_checks` | counter | `result` = `queued`, `duplicate`, `dropped` | что сканер сделал с поездкой на этом тике |
| `tripgo.stale_scan.rows` | histogram, строки | нет | сколько строк сканер прочитал из БД за один тик |
| `tripgo.position_requests.queue.size` | gauge | нет | сколько задач сейчас в очереди |
| `tripgo.position_requests.workers.active` | gauge | нет | сколько воркеров заняты |
| `tripgo.position_requests` | counter | `result` = `success`, `error`, `dropped` | чем закончилась попытка запросить координату |
| `tripgo.position_requests.duration` | histogram, секунды | `result` | сколько занял вызов Push Service |

Два gauge читаются в момент сбора метрик, то есть раз в 10 секунд, поэтому на
графике видны значения на момент сбора, а не пики между сборами.

Тик сканера пишется как спан `positions.scan`. Обработка задачи воркером это
отдельный корневой спан `positions.process`, связанный со спаном тика через
span link, а не через родителя: обработка идёт асинхронно и живёт дольше
прохода, который её породил. Вызов Push Service это дочерний спан
`push.request_position`.

Warn пишется при отбрасывании задачи из-за полной очереди и при ошибке запроса
в Push Service. Error пишется, если сканер не смог прочитать выборку, кроме
случая, когда причина в остановке сервиса. Info пишется при старте и остановке
компонента.

### Упрощения

- Отметку об отправленной команде не храним, поэтому период тикера заменяет
  паузу между повторными командами. В проде хранят время последней отправки и
  разводят два интервала.

### Как проверить

Окружение и сервис:

```bash
tripgoctl environment start
set -a; source .env; set +a
make run
```

В другом терминале создайте поездку и не отправляйте координаты:

```bash
curl -sS -X POST localhost:8080/api/v1/trips -H 'content-type: application/json' \
  -d '{"user_id":"2d1c1c3a-8f43-4d6e-9a53-3c1f2f3b1a10","driver_id":"7a3f5d0e-2f1b-4c53-b3a7-6a1d9d3e4f21","start_point":{"latitude":56.8,"longitude":60.6},"end_point":{"latitude":56.9,"longitude":60.7},"price":500}'
tripgoctl environment logs push-service
```

Через `POSITION_STALE_AFTER` в логе заглушки появляется `REQUEST_POSITION`, и не
чаще одного раза за `POSITION_CHECK_INTERVAL`. Чтобы не ждать, запустите сервис
напрямую с короткими интервалами (значения из `.env` имеют приоритет только у
целей `make`):

```bash
set -a; source .env; set +a
POSITION_CHECK_INTERVAL=2s POSITION_STALE_AFTER=4s go run ./cmd/trip-service
```

Если слать координаты каждые 5 секунд, команд быть не должно:

```bash
while true; do
  curl -sS -o /dev/null -X POST localhost:8080/api/v1/trips/$TRIP_ID/positions \
    -H 'content-type: application/json' \
    -d "{\"coordinates\":{\"latitude\":59.93,\"longitude\":30.33},\"recorded_at\":\"$(date -u +%FT%TZ)\"}"
  sleep 5
done
```

Нагрузка: 200 активных поездок без координат при очереди на 10 задач и
заглушка, которая отвечает 3 секунды:

```bash
curl -fsS -X POST "$PUSH_HTTP_URL/admin/behaviour" -H 'content-type: application/json' -d '{"latency_ms":3000}'
POSITION_QUEUE_SIZE=10 POSITION_CHECK_INTERVAL=2s POSITION_STALE_AFTER=2s PUSH_REQUEST_TIMEOUT=5s go run ./cmd/trip-service
```

```bash
for i in $(seq 200); do
  curl -s -o /dev/null -X POST localhost:8080/api/v1/trips -H 'content-type: application/json' \
    -d "{\"user_id\":\"$(cat /proc/sys/kernel/random/uuid)\",\"driver_id\":\"$(cat /proc/sys/kernel/random/uuid)\",\"start_point\":{\"latitude\":1,\"longitude\":1},\"end_point\":{\"latitude\":2,\"longitude\":2},\"price\":1}"
done
```

В Grafana растёт `tripgo_stale_checks_total{result="dropped"}`, очередь доходит
до 10, активных воркеров 4, а `/health` и `GET` поездки отвечают за
миллисекунды. После проверки верните заглушку в исходное состояние:

```bash
curl -fsS -X POST "$PUSH_HTTP_URL/admin/behaviour" -H 'content-type: application/json' -d '{"latency_ms":0}'
```

`SIGTERM` под нагрузкой завершает процесс в пределах `SHUTDOWN_TIMEOUT`.

## Наблюдаемость

Трейсы, метрики и логи уходят в коллектор по OTLP/HTTP, адрес берётся из
`OTEL_EXPORTER_OTLP_ENDPOINT`. Коллектор отдаёт трейсы в Jaeger и метрики в
Prometheus, Grafana читает Prometheus.

Если коллектор недоступен, сервис всё равно запускается и отвечает на запросы.
SDK раз в несколько секунд пишет в stderr ошибку отправки, на работу ручек это
не влияет.

### Трейсы

Middleware `Tracing` создаёт на каждый запрос корневой спан с именем
`{method} {route}`, например `POST /api/v1/trips`. В имени стоит шаблон
маршрута, а не URL. На ответах 5xx и при панике спан получает статус
`codes.Error` и атрибут `error.type`. Заголовок `traceparent` во входящем
запросе продолжает чужой трейс.

Каждый запрос к БД становится вложенным спаном. Это делает `otelpgx` на
уровне пула соединений. Небольшая обёртка в `infra/postgres/tracer.go`
дописывает в спан `db.operation.name` и `db.collection.name` (имя таблицы
берётся из текста SQL) и `error.type` при ошибке. В спан попадает текст
запроса с плейсхолдерами, значений параметров там нет.

Опрос устаревших поездок пишет свои спаны, они описаны в разделе «Опрос
устаревших поездок»: тик сканера, обработка задачи воркером (связана с тиком
через span link) и вызов Push Service.

### Метрики

| Имя | Тип | Единица | Лейблы |
|---|---|---|---|
| `http.server.request.duration` | histogram | секунды | `http.request.method`, `http.route`, `http.response.status_code` |
| `http.server.active_requests` | up-down counter | штуки | `http.request.method`, `http.route` |
| `db.client.operation.duration` | histogram | секунды | `db.operation.name`, `db.collection.name`, `error.type` |
| `tripgo.trips.created` | counter | штуки | нет |
| `tripgo.trips.completed` | counter | штуки | нет |
| `tripgo.trips.active` | gauge | штуки | нет |
| `tripgo.positions.saved` | counter | штуки | нет |
| `tripgo.stale_checks` | counter | штуки | `result` |
| `tripgo.stale_scan.rows` | histogram | строки | нет |
| `tripgo.position_requests.queue.size` | gauge | штуки | нет |
| `tripgo.position_requests.workers.active` | gauge | штуки | нет |
| `tripgo.position_requests` | counter | штуки | `result` |
| `tripgo.position_requests.duration` | histogram | секунды | `result` |

В `http.route` всегда шаблон маршрута, без подставленного `tripId`. Счётчики
`tripgo.trips.created` и `tripgo.trips.completed` увеличиваются в `usecase`
после успешного коммита. Gauge `tripgo.trips.active` при каждом сборе метрик
(раз в 10 секунд) считает активные поездки запросом `count(*)` в БД, поэтому
после перезапуска сервиса значение остаётся верным. В
Prometheus метрики видны как `http_server_request_duration_seconds` и
`tripgo_trips_created_total`.

Счётчик `tripgo.positions.saved` увеличивается в `usecase` после успешного
коммита. Остальные пять метрик опроса описаны в разделе «Опрос устаревших
поездок». Границы корзин гистограммы `tripgo.position_requests.duration`
заданы в секундах (от 5 мс до 10 с), как у `http.server.request.duration`.

### Логи

Логи пишутся через `log/slog` в JSON в stdout. Обёртка над handler достаёт
из `context` идентификаторы спана и добавляет `trace_id` и `span_id`, поэтому
всё, что залогировано с `InfoContext(ctx, ...)` внутри запроса, связано с его
трейсом. Поле `service` задано у логгера один раз.

Middleware `Logging` пишет одну запись `request handled` на запрос с полями
`method`, `route`, `status` и `duration_ms`. Уровень `Info` для ответов 2xx и
4xx, `Error` только для 5xx. Тела запросов и ответов не логируются. События
«поездка создана» и «поездка завершена» пишет `usecase`, а не middleware.

### Middleware

Порядок такой: `Recover`, `Tracing`, `Logging`, `Metrics`, затем роутер.
`Recover` перехватывает панику, пишет стектрейс в лог и отвечает
`500 internal_error`. Остальные три middleware при панике учитывают запрос как
ответ 500, поэтому в трейсе, логе и метриках он не теряется.

Шаблон маршрута определяет сам роутер: до запуска цепочки он ищет подходящий
маршрут в chi и кладёт результат в `context`. Это нужно, потому что маршрут
должен быть известен уже в начале запроса: от него зависят имя спана и лейблы
`http.server.active_requests`. Неизвестному пути достаётся маршрут
`unmatched`, чтобы не создавать новую серию метрик на каждый адрес.

## Тесты

`make test` запускает unit-тесты с `-race -count=2` и показывает покрытие.

- `domain`: табличные тесты завершения поездки и валидации.
- `usecase`: табличные тесты на моках `gomock`, без БД. Покрыты создание,
  занятый водитель, невалидные данные, ошибка репозитория, завершение,
  повторное завершение, поездка не найдена и четыре случая идемпотентности:
  новый ключ, повтор с тем же телом, тот же ключ с другим телом и проигранная
  гонка за ключ.
- `http`: хендлеры через `httptest` с настоящим `domainerror`, отдельные
  таблицы для маппинга ошибок и для middleware (спаны проверяются через
  `tracetest`, метрики через `ManualReader`). Для `create` проверена
  валидация тела: для каждого обязательного поля (включая `latitude` и
  `longitude` в обеих точках) проверены случаи «поля нет» и `null`, а также
  второй объект после тела, мусор после тела, пробелы в конце тела и явные
  нулевые значения.
- `worker/positions`: сканер, очередь и пул проверяются на моках `gomock` и
  ручном тикере, без `time.Sleep`. Тесты синхронизируются каналами и событиями
  метрик, а `goleak.VerifyTestMain` следит, чтобы после тестов не осталось
  горутин. Покрыто: сканер читает все батчи, продолжая после последней строки
  (250 поездок, батч 100, три запроса, ни одна не пропущена), делает ещё один
  запрос после полного последнего батча и перестаёт читать, когда очередь
  заполнилась; повторный тик не добавляет поездку, которая уже в очереди;
  координата между постановкой и обработкой отменяет отправку, в том числе
  устаревшая копия после отмены и повторной постановки; переполнение очереди
  даёт `dropped` и не блокирует сканер; пул обрабатывает N задач ровно
  `POSITION_WORKERS` воркерами; остановка дорабатывает очередь и останавливает
  тикер; когда бюджет остановки истёк, запросы прерываются; ошибка Push
  Service не останавливает воркер; после завершённого запроса поездка снова
  может попасть в очередь; тики не накладываются; спан воркера связан со
  спаном тика через link.
- `gateway/push`: `httptest`: контракт запроса, разбор кодов ответа, закрытый
  сервер, таймаут, отмена контекста и закрытие тела ответа.
- `usecase/position` и `http/position`: валидация тела (для каждого
  обязательного поля случаи «поля нет» и `null`), отмена очереди после успеха,
  404 и 409.
- `config`: значения по умолчанию, переопределение и неверные значения.

`make test-integration` запускает те же тесты и вместе с ними интеграционные
тесты репозитория на PostgreSQL (файлы с тегом `integration`). Цель сама
загружает `.env`, нужны только применённые миграции. Каждый тест создаёт
поездки со случайными UUID и удаляет их за собой, поэтому тесты можно
запускать повторно. Среди них тест отката транзакции: оба `INSERT` (в `trips`
и в `trip_status_history`) откатываются вместе, и тест параллельного `finish`.
Для ключей идемпотентности проверено, что просроченный ключ не находится и его
можно занять заново, что при параллельном `Reserve` на просроченный ключ
побеждает ровно один запрос, что `DeleteExpiredKeys` удаляет только
просроченные ключи (этот тест идёт на отдельном репозитории с огромным TTL, чтобы
не задеть чужие ключи общей БД). Репозиторий с таймаутом в 1 нс возвращает
`context.DeadlineExceeded`.

Интеграционные тесты репозитория дополнены координатами. Проверены:
сохранение обновляет `last_position_at`, а откат транзакции откатывает и
точку, и `last_position_at`; старая координата, пришедшая позже свежей,
`last_position_at` не меняет; маршрут отсортирован по `recorded_at` и `id`;
выборка для опроса отбирает только активные поездки, которые молчат дольше
порога, самые молчаливые первыми; каждый SQL-запрос идёт под своим таймаутом.

Тест остановки контейнера (`internal/container`) поднимает сервис на настоящей
БД, отправляет сигнал остановки и проверяет `goleak`. Адрес коллектора в нём
заменён на недоступный, а срок хранения ключей идемпотентности сделан очень
большим. Первое нужно потому, что keep-alive соединение экспортёра
OpenTelemetry к коллектору живёт после последнего сброса метрик, и `goleak`
посчитал бы его утечкой, хотя оно не относится к коду сервиса. Второе нужно,
чтобы фоновая очистка ключей при старте не удалила ключ, который в этот момент
использует интеграционный тест репозитория на общей БД.

`make lint` запускает `golangci-lint` с конфигом курса.

Сборка двухэтапная: `golang:1.27-alpine` компилирует статический бинарник,
в финальном образе на `gcr.io/distroless/static-debian12:nonroot` лежит только
он, без Go-тулчейна, оболочки и исходников, процесс запускается от
пользователя `nonroot`. Размер финального образа: 15.9 МБ в сжатом виде,
52 МБ на диске (по выводу `docker images`).

Если PostgreSQL поднят на хост-машине (как при локальной разработке через
`tripgoctl`), значение `localhost` в `DATABASE_URL` внутри контейнера
указывает на сам контейнер, а не на хост. Подставьте `host.docker.internal`:

```bash
docker run --rm -p 8080:8080 --env-file .env \
  -e DATABASE_URL="${DATABASE_URL//localhost/host.docker.internal}" \
  -e PUSH_HTTP_URL="${PUSH_HTTP_URL//localhost/host.docker.internal}" trip-service
```

## Решения

### Уровень изоляции транзакций

`Read Committed`. Запрет двух активных поездок у одного водителя обеспечивает
partial unique index на уровне БД, и это не зависит от уровня изоляции. При
создании поездки решение по ключу идемпотентности принимает один условный
оператор `INSERT ... ON CONFLICT ... DO UPDATE ... WHERE`, остальные
операторы ничего не читают для принятия решения: дубль активной поездки ловит
уникальный индекс. Именно `Read Committed` делает этот оператор корректным при гонке:
проигравший запрос заново проверяет `WHERE` на закоммиченной версии строки
победителя и получает ноль затронутых строк, тогда как под `Repeatable Read`
или `Serializable` он получил бы ошибку сериализации (`40001`). В `finish` есть
цепочка «прочитал, решил, записал», но её защищает
`SELECT ... FOR UPDATE`: параллельный запрос ждёт снятия блокировки, потом
видит уже завершённую поездку и получает `trip_completed`. `Serializable`
добавил бы только повторы транзакций при конфликтах, а то, что нужно
сервису, уже даёт связка `Read Committed`, индекса и блокировки строки.

### Менеджер транзакций

Пакет `internal/infra/postgres/transaction`, тип `Manager` с методом
`Do(ctx, fn)`. Интерфейс `txManager` объявляют сами `usecase`, которым нужны
транзакции. Транзакция помещается в `context.Context` через неэкспортируемый
ключ, чтобы её нельзя было случайно перепутать с чужим значением в
контексте. Репозиторий получает исполнителя запроса (`*pgxpool.Pool` или
`pgx.Tx`) через метод `Manager.Executor(ctx)`: он проверяет контекст, и если
транзакция там уже есть, использует её, иначе обращается напрямую к пулу
соединений. Если `fn` вернула `nil`, выполняется `COMMIT`; если вернула ошибку
или запаниковала, выполняется `ROLLBACK`, при панике через `defer`/`recover` с
повторным `panic` после отката, чтобы вызывающий код узнал о ней. Вложенный
вызов `Do` определяется по наличию транзакции в переданном `ctx`: если она
уже есть, `Do` не открывает новую, а выполняет `fn` в существующей.

### Запрет двух активных поездок на одного водителя

Обеспечивает partial unique index:

```sql
CREATE UNIQUE INDEX trips_one_active_per_driver_idx
    ON trips (driver_id)
    WHERE status = 'active';
```

Уникальность требуется только среди строк со `status = 'active'`; завершённых
поездок у водителя может быть сколько угодно. Postgres проверяет это условие
атомарно при `INSERT`, поэтому два параллельных запроса на одного водителя
гарантированно дают одну созданную поездку и одну ошибку `23505`. Репозиторий
превращает её в `ErrDriverBusy` (и дальше в `409 driver_busy`), только если
нарушен именно этот индекс: другое нарушение уникальности стало бы `500`, а
не ложным «водитель занят».

### Идемпотентность создания поездки

Ключи лежат в таблице `idempotency_keys` (`key UUID PRIMARY KEY`,
`request_hash`, `response_body`, `created_at`). Логика живёт в `usecase/trip/create`, хэш
тела считает ручка.

Если в запросе есть `Idempotency-Key`, `usecase` сначала ищет ключ. Если
запись есть и хэш совпал, он возвращает ту же поездку с кодом `200`; если хэш
другой, возвращает `ErrIdempotencyConflict`. Поездка при повторе читается из
БД по `trip_id`, который лежит в `response_body` как `{"trip_id": "..."}`.
Поэтому, если поездку успели завершить, повторный запрос покажет актуальный
статус.

Если живой записи нет (ключа нет или он просрочен), в одной транзакции
выполняются три шага: `Reserve` (занять ключ с хэшем тела), `Save` поездки и
`Complete` (запись `trip_id`). Если `Reserve` ничего не вставил и не обновил,
значит параллельный запрос с тем же ключом уже занял его и живой ключ
существует. `Reserve` идёт первым шагом, поэтому поездка к этому моменту ещё не
создана: `usecase` откатывает транзакцию, заново читает ключ и отвечает как на
обычный повтор.

`Reserve` выполняется одним оператором (`$4` это `IDEMPOTENCY_KEY_TTL` в
секундах, `$3` это `'{}'`):

```sql
INSERT INTO idempotency_keys (key, request_hash, response_body)
VALUES ($1, $2, $3)
ON CONFLICT (key) DO UPDATE
SET request_hash = EXCLUDED.request_hash,
    response_body = EXCLUDED.response_body,
    created_at = now()
WHERE idempotency_keys.created_at <= now() - make_interval(secs => $4)
```

Это `INSERT ... ON CONFLICT (key) DO UPDATE ... WHERE`, а не перехват ошибки
`23505`. В Postgres ошибка внутри транзакции переводит её в прерванное
состояние, а так конфликт с живым ключом просто даёт ноль затронутых строк, и
транзакция остаётся рабочей. `RowsAffected() == 1` означает, что ключ занят:
он был новым или просроченным. Ноль означает, что существует живой ключ.
Если конкурирующая транзакция ещё не завершилась, вставка ждёт её конца. Гонка
решается уникальным индексом на уровне БД, а не блокировками в коде.

Срок жизни проверяется при чтении. `Find` возвращает ключ, только если
`created_at > now() - make_interval(secs => TTL)`, где TTL берётся из `IDEMPOTENCY_KEY_TTL` (по
умолчанию `24h`). Просроченный ключ для `usecase` выглядит как отсутствующий,
поэтому повторный запрос создаёт новую поездку, даже если тело отличается.

Повторное занятие просроченного ключа атомарно и при конкуренции. Если
несколько запросов одновременно приходят на один просроченный ключ, Postgres
блокирует конфликтующую строку, один запрос её обновляет и побеждает, а
остальные после снятия блокировки заново проверяют `WHERE` на уже закоммиченной
свежей версии строки, не проходят проверку и получают ноль строк. Дальше они
идут по пути проигравшего гонку: откат, повторное чтение ключа, ответ как на
обычный повтор.

Фоновая очистка нужна только для экономии места. `container.Run` запускает
горутину, которая вызывает `DeleteExpiredKeys` (`DELETE ... WHERE created_at <=
now() - make_interval(secs => TTL)`) при старте и затем раз в час. Она безопасна рядом с `Reserve`:
обе операции блокируют строку, а только что занятая заново строка условию
удаления уже не соответствует. От очистки корректность не зависит, потому что
срок проверяется на каждом чтении.

Время `started_at` и `finished_at` округляется до микросекунд перед записью:
Postgres хранит именно их, и ответ на создание совпадает с ответом на повтор
запроса до последней цифры.

### Таймаут запросов к БД

`DATABASE_QUERY_TIMEOUT` действует на каждую операцию с БД. Для этого у
`transaction.Manager` есть метод `WithTimeout(ctx)`: он возвращает
`context.WithTimeout`, производный от контекста запроса или транзакции.
Репозиторий получает его через интерфейс `executorProvider`, который объявлен
у потребителя, в `repository/trip/contract.go`, и после этой правки получил
метод `WithTimeout` рядом с `Executor`. Через него работают все методы
`repository/trip`: `Save` (вставка поездки и вставка в историю статусов),
`Update`, `GetByID` и `GetForUpdate`, `CountActive`, `Find`, `Reserve`,
`Complete`, `DeleteExpiredKeys`, а также `SavePosition` (каждый из двух
запросов под своим таймаутом), `ListPositions` и `FindStale`. `Save` и `Update` дают основному оператору и
вставке в историю статусов отдельные таймауты, а не один на двоих.

Сам менеджер транзакций применяет тот же таймаут к `BEGIN`, `COMMIT` и
`ROLLBACK`. `ROLLBACK` работает под собственным таймаутом и не зависит от
отмены контекста запроса, поэтому откат выполняется, даже если клиент уже
отключился. Контейнер больше не
оборачивает в свой таймаут колбэк gauge `tripgo.trips.active`, этим занимается
`CountActive`. Значение должно быть положительным, иначе запуск завершается
ошибкой. Превышение таймаута клиент видит как `500 internal_error`, причина
(`context deadline exceeded`) уходит в лог. Проверка `/ready` использует
отдельный `DATABASE_CONNECT_TIMEOUT`, а не `DATABASE_QUERY_TIMEOUT`.

### Сохранение координаты

Координата сохраняется в одной транзакции через менеджер транзакций. Сначала
выполняется `UPDATE trips SET last_position_at = GREATEST(last_position_at, $1)
WHERE id = $2 AND status = 'active'`, потом `INSERT` в `trip_positions`.
`UPDATE` идёт первым, потому что он берёт блокировку строки поездки. Если
параллельно завершают поездку, одна операция ждёт другую. Проигравшая заново
проверяет `status` на закоммиченной версии строки (поэтому здесь, как и в
`finish`, нужен `Read Committed`) и получает ноль строк. Ноль строк
разбирается так: поездки нет, значит `404`, поездка завершена, значит `409`.

Сравнение делает SQL. `GREATEST` игнорирует `NULL`, поэтому первая координата
просто записывается, а старая координата, пришедшая позже свежей,
`last_position_at` не меняет. Читать значение в Go и писать его обратно нельзя:
между чтением и записью может проскочить другая координата. Время хранится с
точностью до микросекунд, как в Postgres, и приводится к этой точности до
записи.

Первая координата записывается в `last_position_at` как есть, даже если её
`recorded_at` раньше `started_at`: свежесть поездки считается по
`recorded_at`, а не по времени создания. Такая координата может сразу сделать
поездку «молчащей». Отдельной защиты от этого нет, потому что правдоподобие
координат задание не проверяет.

### Индекс под запрос опроса

Индекс `trips_active_last_activity_idx` частичный: он построен по выражению
`COALESCE(last_position_at, started_at)` и только для `status = 'active'`.
Запрос фильтрует и сортирует по этому же выражению, поэтому индекс отдаёт
строки уже в нужном порядке, от самых молчаливых, а завершённых поездок,
которых со временем большинство, в нём нет. Статус в запросе записан
литералом: если передать его параметром, планировщик с подготовленными
запросами перестаёт использовать частичный индекс. Индекс создаётся отдельной
миграцией через `CREATE INDEX CONCURRENTLY` и без транзакции
(`-- +goose NO TRANSACTION`), чтобы не блокировать запись в `trips`. Результат
`EXPLAIN (ANALYZE)` приведён в описании PR.

Батчи с курсором используют тот же индекс. Условие «пара (время, `id`) больше
курсора» планировщик разбирает на границу по первому полю, которую берёт индекс,
и проверку пары по строке, поэтому начало каждого следующего батча находится
по индексу, а не просмотром всех уже прочитанных строк. Сортировка по `id`
внутри равного времени делается инкрементально, на сотне строк это незаметно.
Отдельного индекса по `(выражение, id)` не заводили.
